# Hub core implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build milestone 1 of orfoni: `orfoni-hub`, which runs Claude Code sessions in tmux, turns their hook events into session states and chat items, sends messages into them, and answers approvals, questions, and plan approvals, driven by a small command-line client.

**Architecture:** The hub is a Node daemon. It starts each session as `claude` in its own tmux session on a dedicated tmux server, with a per-session settings file that points Claude Code's HTTP hooks at the hub on 127.0.0.1. A pure reducer turns hook events into a session state and a chat log. Clients connect through `orfoni-hub connect`, which bridges stdin and stdout to the daemon's Unix socket, so an SSH connection is the only transport.

**Tech Stack:** Node 22, TypeScript (strict, ESM), npm workspaces, vitest, zod, `@anthropic-ai/claude-agent-sdk` pinned to 0.3.310, tmux 3.6, systemd user units.

**Spec:** `docs/design.md`

## Global Constraints

- Every session is an ordinary interactive `claude` process in its own tmux session. The hub never runs Claude in headless mode.
- tmux server socket name `orfoni`. Claude sessions are tmux sessions named `orfoni-<uuid>`. Shells are named `orfoni-<uuid>-sh<n>`. Each tmux session holds exactly one process.
- The tmux server runs as its own systemd user unit, `orfoni-tmux.service`, so restarting the hub never kills a session.
- Hooks reach Claude Code only through a per-session file passed with `--settings`. Do not edit `~/.claude/settings.json` in this milestone.
- The hook server binds `127.0.0.1` only. Default port `47380`, overridable with `ORFONI_HOOK_PORT`.
- The client socket lives at `$XDG_RUNTIME_DIR/orfoni/hub.sock`. State lives in `~/.local/state/orfoni/`.
- Use only these Agent SDK functions: `listSessions()` and `getSessionMessages()`. Use no SDK option the reference marks alpha.
- No Claude Code feature that the docs label research preview or alpha.
- The state file has a `version` field and is written atomically, by writing a temporary file and renaming it.
- The `MessageDisplay` hook entry has `timeout: 2`, and the hub answers it before doing any work.
- The `PermissionRequest` hook entry has `timeout: 3600`.
- Answer an `ExitPlanMode` request with `updatedInput` set to the request's own `tool_input`. A bare `allow` does not close the plan dialog (spike, 2026-10-26).
- Answer an `AskUserQuestion` request with `updatedInput` set to the request's `tool_input` plus an `answers` object that maps each question's text to the chosen option label.
- Pass a session's first message as the positional prompt argument to `claude`, because a paste sent before the input box is ready is lost (spike, 2026-10-26).
- Markdown and commit messages: no em dashes, and no manual line breaks inside a paragraph.

## Review Focus

- A message sent right after a session starts, or while the hub cannot tell whether the input box is ready, must not vanish. Expect `send` to confirm delivery through the `UserPromptSubmit` hook and to report a failure when no confirmation arrives within 5 s. Test in Task 6.
- A multi-line message with quotes, emoji, or a leading `/` or `!` must arrive exactly as typed. Expect the `UserPromptSubmit` prompt, or the bash-mode output for `!`, to match. Test in Task 9.
- An approval answered in the terminal must disappear from every client. Expect the hub to withdraw the request when the matching tool call finishes or the turn ends, and to close the held HTTP request with an empty 200. Test in Task 4.
- Two clients answering the same request must not both win. Expect the first answer to apply and the second to get the error `already_resolved`. Test in Task 4.
- A hub restart during a running turn must not lose the session. Expect the session to keep running in tmux and the hub to list it again, in state `working` until the next hook event says otherwise. Test in Task 9.

### Task 3: Session state machine and chat log

**Files:**
- Create: `hub/src/session/reduce.ts`
- Test: `hub/src/session/reduce.test.ts`

**Interfaces:**
- Consumes: `HookEvent` (Task 2), `SessionStateKind` and `ChatItem` (Task 1).
- Produces:
  - `interface SessionModel { state: SessionStateKind; stateSince: number; claudeSessionId: string | null; chat: ChatItem[]; openRequests: string[]; viewed: boolean }`
  - `type SessionInput = { kind: 'hook'; event: HookEvent; at: number } | { kind: 'request_opened'; requestId: string; item: ChatItem; at: number } | { kind: 'request_closed'; requestId: string; outcome: RequestOutcome | 'withdrawn'; at: number } | { kind: 'viewed'; at: number } | { kind: 'pane_exited'; at: number }`
  - `reduce(model: SessionModel, input: SessionInput): SessionModel`, pure.
  - `emptySession(at: number): SessionModel` with `state: 'idle'`.

The transitions are the table in the design's "Session states" section. These rows pin the details the table leaves open:

| Input | Effect |
|---|---|
| `session_start` with `source: 'clear'` | new `claudeSessionId`, chat becomes `[]`, state `idle` |
| `prompt` | appends a `user` item, state `working` |
| `assistant_text` | appends `delta` to the `assistant` item with the same `messageId`, creating it if needed, and sets `done` on `final` |
| `tool_start`, `tool_end`, `tool_failed` | upserts the `tool` item by `toolUseId` |
| `request_opened` | appends its item, adds the request ID, state `needs_answer` for `question` and `plan` items, else `needs_approval` |
| `request_closed` | sets the item's status, removes the request ID, state `working` when no request stays open |
| `stop` | state `answered`, or `idle` when `viewed` is true |
| `stop_failure` | appends a `notice` item with the error, state `failed` |
| `session_end`, `pane_exited` | state `offline` |
| `viewed` | state `idle` when it was `answered`, and `viewed` becomes true until the next `prompt` |

### Task 4: Pending requests

**Files:**
- Create: `hub/src/requests.ts`
- Test: `hub/src/requests.test.ts`

**Interfaces:**
- Consumes: `HookEvent`, `Decision`, `ChatItem`.
- Produces `class PendingRequests`:
  - `open(sessionId: string, event: Extract<HookEvent, { type: 'permission_request' }>, lastToolStart: { toolUseId: string } | null): { requestId: string; item: ChatItem; response: Promise<HookResponse> }`. The item kind is `question` for `AskUserQuestion`, `plan` for `ExitPlanMode`, and `approval` for every other tool.
  - `decide(requestId: string, decision: Decision): RequestOutcome`, throwing `RequestError` with code `already_resolved` when the request is closed and `wrong_decision` when the decision type does not fit the item kind.
  - `withdrawFor(sessionId: string, event: HookEvent): string[]` returns the IDs it withdrew. A `tool_end` or `tool_failed` withdraws the request linked to that `toolUseId`. A `stop`, `stop_failure`, `prompt`, or `session_end` withdraws every open request of the session.
- Produces `type HookResponse = Record<string, never> | { hookSpecificOutput: { hookEventName: 'PermissionRequest'; decision: { behavior: 'allow' | 'deny'; updatedInput?: unknown; updatedPermissions?: unknown[]; message?: string } } }`. A withdrawn request resolves to `{}`.

A second `decide` throws `already_resolved`. `answer` on an approval throws `wrong_decision`. `withdrawFor` with a matching `tool_end` resolves the response to `{}` and returns the request ID.

### Task 6: Hub daemon

**Files:**
- Create: `hub/src/hub.ts` (the `Hub` class: sessions, requests, broadcasts), `hub/src/hook-server.ts`, `hub/src/client-server.ts`, `hub/src/store.ts`, `hub/src/history.ts`, `hub/src/memory.ts`, `hub/src/main.ts`, `hub/bin/orfoni-hub.js`, `hub/systemd/orfoni-hub.service`
- Test: `hub/src/hub.test.ts`, `hub/src/store.test.ts`

**Interfaces:**
- Consumes: everything from Tasks 1 to 5.
- `Hub` handles each `ClientRequest` method and each hook POST:
  - `startSession` creates a UUID, writes the settings file to `~/.local/state/orfoni/settings/<uuid>.json`, and starts `claude --session-id <claudeUuid> --settings <file> [--name <title>] [--permission-mode <mode>] [<prompt>]` in tmux session `orfoni-<uuid>` with `ORFONI_SESSION=<uuid>` in its environment.
  - `send` refuses with code `not_ready` when the session is `needs_approval` or `needs_answer`. Otherwise it pastes the text. Plain text resolves when a `prompt` hook arrives whose text equals the sent text, and fails with code `not_delivered` after 5 s. Text that starts with `/` or `!` resolves right after the paste, because slash commands and bash mode do not always fire `UserPromptSubmit` (spike, 2026-10-26). A message to an `offline` session first starts `claude --resume <claudeSessionId> --settings <file>` in the same tmux session name and passes the message as the prompt argument.
  - `interrupt` sends `Escape`. `stopSession` kills the tmux session. `openShell` starts `$SHELL -l` in `orfoni-<uuid>-sh<n>` in the session's folder.
  - `openSession` marks the session viewed and returns `{ session: SessionSummary, chat: ChatItem[] }`, where `chat` is the history from `getSessionMessages()` normalized into `ChatItem`s, followed by the live items since the hub started.
  - The hook server answers `POST /hook` with an empty 200 at once, except for `PermissionRequest`, which it holds until `PendingRequests` resolves the response.
- `store.ts`: `loadState(path): Promise<HubState>` and `saveState(path, state): Promise<void>`, where `HubState = { version: 1; sessions: { id, projectDir, title, claudeSessionId, createdAt }[] }`. A missing file gives an empty state. A file with another version or invalid JSON is renamed to `state.json.broken-<timestamp>` and an empty state is used, with a log line.
- `history.ts`: `normalizeHistory(messages: SessionMessage[]): ChatItem[]` turns the output of `getSessionMessages()` into chat items. User text becomes `user`, assistant text becomes `assistant` with `done: true`, a `tool_use` block becomes a `tool` item, and the matching `tool_result` fills its `output` and sets `status` to `done`, or `failed` when `is_error` is true. Thinking blocks and system messages are dropped, except a compaction summary, which becomes a `notice`.
- `memory.ts`: `paneMemory(panePid: number): Promise<{ currentBytes: number; oomKills: number } | null>` reads `/proc/<pid>/cgroup`, then `memory.current` and the `oom_kill` line of `memory.events` under `/sys/fs/cgroup`.
- On start the hub loads the state, lists tmux sessions, and marks each known session `working` when its tmux session exists and `offline` when it does not.
