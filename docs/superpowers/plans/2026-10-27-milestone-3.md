# Milestone 3 implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show at a glance what each session is about and how far it has got: a short AI summary per session, Claude's task progress, memory use per session, and which answers you have not read, kept across hub restarts.

**Architecture:** The hub computes everything and puts it on `SessionSummary` (`summary`, `tasks`, `memory`, added in commit 7eeee9d), plus a `hubStatus` request for the VPS memory and the summary budget. The app only displays it.

**Tech Stack:** as in milestones 1 and 2, plus `@anthropic-ai/sdk` in the hub.

**Spec:** `docs/design.md`, sections "Summaries", "Memory guardrails", and "Session states".

## Global Constraints

- Summaries use the Claude API with the model `claude-haiku-5-5`, overridable with `ORFONI_SUMMARY_MODEL`. The design fixes Haiku 5.5 because 300 summaries a day must fit a $100 monthly API budget.
- The API key is read from `~/.config/orfoni/anthropic-api-key` (mode 0600), or from `ANTHROPIC_API_KEY` when set. Without a key, summaries stay `null`, the hub logs that once, and `hubStatus` reports `enabled: false`. The key never appears in logs, errors sent to clients, or the state file.
- A summary is written when a turn ends (`Stop`) and when a session starts waiting on you, at most once per session every 20 seconds, with at most one request in flight per session. A daily cap of 1,000 summaries and $2 of estimated spend stops further summaries until the next day.
- The summary input is the session title, the folder name, the last 6 user messages, and Claude's final reply, cut to 8,000 characters in total. The output is `about` (what the session is about) and `status` (where it stands), each one sentence.
- A refusal or an API error keeps the previous summary and logs the error without the key.
- Task progress comes from the `TaskCreated` and `TaskCompleted` hooks. `tasks` is `null` until the conversation creates a task. A new conversation after `/clear` starts again at `null`.
- Memory comes from each session pane's cgroup (`memory.current`, `memory.max`, and the `oom_kill` count in `memory.events`), read every 5 seconds. The hub broadcasts `sessionUpdated` when memory changed by more than 10 percent or 50 MB, and adds a chat notice when the `oom_kill` count grows.
- Read state survives a hub restart: the hub stores, per session, when its last turn ended and when a client last viewed it, and derives `answered` against `idle` from those after a restart.
- The state file moves to `version: 2`. A version 1 file is migrated, never set aside.
- No em dash characters in code, docs, UI text, or commit messages. Markdown paragraphs stay on one line.

## Review Focus

- The API key is missing, wrong, or out of credit. Expect the sessions to keep working, summaries to stay as they were, and one clear log line, never the key itself.
- Many turns end in a burst, for example ten sessions finishing within a minute. Expect at most one summary per session per 20 seconds, and the daily cap to hold.
- The hub restarts with a version 1 state file. Expect every session to survive with its read state guessed as read.
- A process in a session is killed for using too much memory. Expect a notice in that session's chat and its memory on the row.
- A session that never creates a task shows no progress bar at all.

- [ ] **H3. Tests first, with cgroup and meminfo files in a temporary folder.
- [ ] **H4. Read state and the version 2 state file**, with the migration. Tests first, including a version 1 file from milestone 1.
- [ ] **H5. Live check.** With the installed hub, start a session, let a turn end, and see `summary`, `tasks` (by asking Claude to create two tasks with TaskCreate and complete one), and `memory` arrive. Skip only the summary part when no key exists, and say so.

### App tasks

- [ ] **A1. Session row:** the summary's `about` on a second muted line, task progress as `3/7`, and memory when above 1 GB or after an out-of-memory kill. An `answered` session stands out until opened.
- [ ] **A2. Session header:** the summary's `status`, a progress bar for the tasks, and a memory meter against `maxBytes` that turns to a warning colour above 80 percent.
- [ ] **A3. Status bar:** VPS memory from `hubStatus`, refreshed every 30 seconds, and whether summaries are on, with today's spend.
- [ ] **A4. Window title:** `orfoni (n)`, where n counts sessions that need you or have an unread answer. In Tauri, set the native window title too.
- [ ] **A5. Checks.** Component tests for A1 to A4 first. Extend the Playwright checks with task progress and memory on a real session, and with the summary when the hub has a key.
